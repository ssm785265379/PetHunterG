# 复原一个停服老 APK：视频口播稿与制作手册

> 案例：宠物猎人G（Android AIR 游戏，官方停服）的本地离线复原。
> 这份文档既是**口播稿**，也是**拍摄清单**与**技术底稿**。目标时长 18–22 分钟。
> 免责声明：仅用于自己拥有、已停服、且不对外分发的单机环境；不传播游戏资产、不架公网私服、不复刻付费内容。

## 1. 工具清单（按阶段）

### 1.1 拆包 / 反编译

| 工具 | 用途 | 本项目的具体用法 |
|---|---|---|
| `apktool` / `unzip` | 看 APK 结构、manifest、so、assets | 确认是 AIR 包、找 `libCore.so`、定位 `assets/` 里的 SWF |
| **FFDec（JPEXS）** | 反编译/回编译 SWF、导出 AS3、替换类 | `java -jar ffdec.jar -export script out app.swf`；`-importScript` 回写 |
| `jadx`（可选） | 如果 Java 层有逻辑 | 本项目 Java 层很薄，用不上 |
| `strings` / 十六进制 | 找 URL、IP、密钥常量 | 从 SWF 里抠出 4 个硬编码服务器 IP |

### 1.2 重打包 / 签名

| 工具 | 用途 | 注意 |
|---|---|---|
| **HARMAN AIR SDK 51.x** | 把 AIR 3.4 的老运行库换成新运行库 | 老包在 Android 16 上因私有 `libstagefright.so` 起不来 |
| `adt.bat -package -target apk -arch armv7` | 打 APK | 需要 JDK 17；Java 25 会让 Gradle 报 class file 69 |
| `keystore`（pkcs12） | 自签名 | 密码放本地文件，**不写进脚本、不入库** |
| `aapt dump badging` | 验包名/版本/启动 Activity | 打完必须验，别只看文件大小 |
| `adb` | 装机、`reverse` 端口、logcat | 安装要用户点系统弹窗，命令返回≠装好 |

### 1.3 联调 / 观察

| 工具 | 用途 |
|---|---|
| `mitmproxy` / `Charles` / `tcpdump` | 抓 HTTP 明文请求（本项目就是 `POST /flash.do`） |
| `adb logcat` | 看客户端 trace、`#1065` 之类 AS3 异常 |
| **AIR ADL（桌面运行时）** | 不打包、不装机，2 秒看画面；窗口必须 640×960 |
| 截图/录屏（PowerShell + `System.Drawing`） | 自动抓窗口、做前后对比 |

### 1.4 服务端 / 工程化

| 工具 | 用途 |
|---|---|
| Python + Flask + SQLite | 本地协议服务与存档；**先只读，后写** |
| pytest | 每个命令一条契约测试；测试数字只增不减 |
| git + worktree | 一任务一分支一 worktree，冲突只在合并时解决 |
| PowerShell 脚本 | 一键起服务、起窗口、截图、建 lane |

## 2. 总流程（口播时配一张流程图）

```text
拿到 APK
  ├─ 1. 看它能不能装/能不能起  →  不能：换运行库重打包（AIR SDK）
  ├─ 2. 能起但连不上服务器    →  抓包，找 base URL 与协议入口
  ├─ 3. 抓不到（证书/加密）   →  静态分析：从 SWF/配置里找字段消费者
  ├─ 4. 本地起一个"回声服务"  →  只回形状正确的空结构，先不崩
  ├─ 5. 逐命令对齐：请求 → 响应 → 界面 → 存档
  ├─ 6. 把业务错误做成协议错误（HTTP 200 + -1:id）
  ├─ 7. 数值与规则：配置表优先，help 文本次之，剩下标 LOCAL
  └─ 8. 工程化：桌面预览、测试、看板、合并门
```

### S1 先定边界（0:40–2:00）

**画面**：一张"能做 / 不能做"的表。

**口播**：

> 先把边界说清楚，不然做着做着就变味了。

### S2 第一关：它为什么装不上、起不来（2:00–4:30）

**画面**：`adb install` 失败 → `logcat` 里 `libCore.so` / `libstagefright.so` → AIR SDK 目录。

**口播**：

> 老 APK 的第一道坎，往往不是服务器，是**运行库**。
> 这个包是 Adobe AIR 3.4 的，它依赖一个叫 `libstagefright.so` 的私有库。Android 16 上这个库早就没了，所以一启动就崩。
> 解法不是改代码，是**换运行库**：用 HARMAN 的 AIR SDK 51 把资源和描述文件重新打一遍包。
> 注意三件事：第一，JDK 要用 17，25 会在 Gradle 报 class file 69；第二，先旁装一个新包名，别覆盖原包；第三，安装一定要在手机上点"安装/打开"，命令行返回成功不等于装好了。

**演示**：
1. `aapt dump badging` 看原包；
2. 展示 `PetHunter-app.xml` 里 `minSdkVersion/targetSdkVersion`；
3. `adt -package` 一条命令；
4. 手机安装、启动、停在"连接超时"——这是**运行成功**，不是失败。

**字幕**：能启动 ≠ 能玩；但能启动是第一个里程碑。

### S3 第二个里程碑：让画面能快速出现（4:30–7:00）

**画面**：改一次 SWF 要 40 秒打包 + 2 分钟装机 → 改成桌面 ADL，2 秒出画面。

**口播**：

> 接下来会改几十次客户端。如果每次都打 43MB 的 APK、再装机，一天什么都干不了。
> AIR 有个桌面运行时叫 ADL，可以直接跑 SWF。我把服务器地址改到本机，窗口固定 640×960——因为 SWF 的原生舞台就是 640×960，你用 480×854，按钮位置全偏。
> 这一步是整条流水线里性价比最高的：**改代码 → 2 秒看到画面**。

**演示**：
1. `dev-desktop.ps1 -Label main -Port 8080`；
2. 窗口出现；
3. 改一个坐标，重跑，画面变化；
4. 展示 `adl.log` / `adl.log.err`（AS3 的 `trace` 在 `.err` 里）。

**顺带一个坑**（字幕）：用脚本"同步等待"启动 ADL 会卡住，因为 `adl64` 会继承调用方的 stdout 句柄；要用 `Start-Process` 分离，再等 pid 文件。

### S4 第三个里程碑：找到协议入口（7:00–10:00）

**画面**：抓包 → `POST /flash.do` → 请求体 `m=show&showId=510&uid=...` → 响应 `510\t{...}`。

**口播**：

> 客户端能起来了，但它还在找那个已经关掉的服务器。第一件事是找它把请求发到哪。
> 抓包能看到明文 HTTP：所有请求都打到一个 `flash.do`，用 `m=show` 加一个 `showId` 区分功能。
> 响应更有意思：它不是纯 JSON，而是**命令号 + Tab + JSON**。这个 Tab 非常关键，后面会救我们一次。
> 我们先不实现任何业务，只起一个"回声服务"：收到什么命令，就回**形状正确**的空结构。目标是——客户端别崩。

**演示**：
1. mitmproxy 抓一条 `showId=22`（背包）；
2. 本地 Flask 打印 "command=show showId=22"；
3. 返回 `22\t{"list":[],"bag_size":0,...}`，客户端不再报错；
4. 强调：**HTTP 200 不是成功**，只是传输成功。

**字幕**：先让界面"有形状"，再让它"有内容"。

---

### S5 对齐协议：一个字段一个字段地找消费者（10:00–13:00）

**画面**：左边 FFDec 里 `BagListUI.as` 读 `param2.list`；右边 Flask 返回 `list`；中间是界面截图。

**口播**：

> 协议怎么对齐？不是看服务端"应该返回什么"，是看**客户端到底读了什么**。
> 比如背包页，反编译出来它读 `param2.list`，每个元素读 `index/id/icon/count`，还有一个 `on` 字段控制灰不灰。
> 那我就只回这些字段。多回没用，少回就崩。
> 更隐蔽的是**空值崩溃**：有的页面没有判空，直接 `param2.list.length`，你回 `{"value":"ok"}` 它当场 `TypeError`，看起来就是"点了没反应"。
> 所以我的规则是：**每个命令，先在客户端找到消费者，再写响应**。找不到消费者的字段，一律不猜。

**演示**：
1. FFDec 搜索 `param2.list`；
2. 对应字段表（`docs/protocol-*.md` 里的"客户端读取"列）；
3. 本地改一个字段名，界面立刻空白——反向证明契约。

**字幕**：字段契约不是文档写出来的，是**改坏一次验证出来的**。

### S6 把"错误"还给玩家（13:00–15:00）

**画面**：用道具失败，界面毫无反应 → 日志里 `-1:300` → 修成 `-1\t-1:300` → 界面弹提示。

**口播**：

> 这一段是我觉得最值钱的坑。
> 业务错误本来应该弹一句"体力已满"。但这个客户端先按 Tab 切命令，再切数据。服务端回了一个**没有 Tab** 的 `-1:300`，客户端一切，数据段变成字符串 `"null"`，于是"这不是错误"，整条提示被吞了。
> 玩家看到的是：道具没扣、也没提示。你会以为是扣减逻辑错了，其实是**错误协议格式错了**。
> 修法只有一行：所有错误统一回 `-1\t-1:<错误号>`，错误号用客户端自带 `error.txt` 里的键。这样服务端日志里也能看到 `PROTOCOL_ERROR`，排查从"猜"变成"读"。

**演示**：
1. 故意回裸 `-1:300`，界面无反应；
2. 改成带 Tab，界面弹出"体力充沛"；
3. `grep PROTOCOL_ERROR` 日志。

**字幕**：**HTTP 200 + 业务错误** 是最容易骗过自己的组合。

### S7 数值与规则：配置表 > 帮助文本 > 你的设计（15:00–18:00）

**画面**：`pet.txt` / `skill.txt` / `help.txt` 三张表 → 一张"证据等级"表 → 规格文档。

**口播**：

> 到了数值层，最容易犯的错是"我觉得应该是这样"。
> 我的顺序是：**随包配置表**优先，因为它是原厂的；其次是**游戏内帮助文本**，它经常写着公式；最后才是我自己设计，而且必须标 `LOCAL DEFAULT`。
> 但帮助文本也会骗人：这个游戏的帮助写着"1500 世代有 30 个特性"，可它自己的公式是 `√世代+1`，1500 代应该是 39。五个示例里只有两个对得上。所以**帮助文本只采信能被公式或数据自证的部分**。
> 配置表也有陷阱：怪物表的六维是照宠物表抄的，但**列序不一样**。你按宠物表的列序读，数值全错。这种坑只能靠"同一行拿两张表交叉验证"发现。

**演示**：
1. `help.txt` 第 10 条与公式对照表；
2. `monster.txt` 与 `pet.txt` 列序对比；
3. 规格文档里的【表】【包】【码】【本地】标记。

**字幕**：**能自证的才叫证据，不能自证的叫设计。**

| 10 | "重启了怎么还是旧行为" | 旧进程占着端口（`SO_REUSEADDR`） | 按端口精确杀进程 + 单实例 | 先看进程启动时间，再怀疑代码 |

## 5. 通信协议对齐方法论（独立小节，可单独出续集）

### 5.1 四步法

1. **抓包**：确定入口 URL、方法、参数名。明文 HTTP 最好；HTTPS 就先找证书固定/绕过，绕不过就转静态分析。
2. **静态消费**：在反编译代码里搜"响应字段名"，找到**谁读它**。没有消费者的字段不实现。
3. **回声→真值**：先回空结构让界面不崩，再逐字段填真值，每填一个截一张图。
4. **错误协议**：把失败也当成协议的一部分；HTTP 200 + `-1:<id>`，错误号用客户端自带的错误表。

### 5.2 本项目协议骨架（示例）

```text
POST /flash.do
m=show & showId=<命令号> & uid=<角色> & ...其他字段

响应：  <命令号>\t{json}
错误：  -1\t-1:<error.txt 的键>
```

客户端**先按 Tab 切命令号**，再解析 JSON——这就是为什么"裸 `-1:300`"会被吞。

### 5.3 字段契约表模板

| 字段 | 客户端读取位置 | 类型 | 为空时行为 | 服务端来源 | 证据 |
|---|---|---|---|---|---|
| `list[].index` | `BagListUI.as:219` | int | 跳过该项 | `inventory.id` | 【包】 |
| `on` | `PropItem.as:328` | 0/1 | 不禁用 | 效果规则是否存在 | 【包】+【码】 |
| `bag_size` | `BagListUI.as:88` | int | 显示 0/100 | 过滤后总数 | 【码】 |

### 5.4 不可信信号清单

- HTTP 200：只代表传输成功。
- 单元测试通过：只代表服务端逻辑自洽。
- 数据库写成功：只代表事务提交。
- 客户端不报错：可能只是错误被吞了。
- 你觉得"应该是这样"：不算证据。

**唯一可信的是四件套**：请求 + 响应 + 界面 + 存档。

## 6. 证据分级（贯穿全片的方法论）

| 标记 | 含义 | 能否质疑 |
|---|---|---|
| 【表】 | 随包配置表原值 | 否（事实） |
| 【包】 | 反编译客户端读到的消费逻辑 | 否（事实） |
| 【码】 | 当前服务端实现（不是原服） | 是（可改） |
| 【用户】 | 用户口述的规则 | 是（需复核） |
| 【本地】 | LOCAL DEFAULT，本地设计 | 是（随便改） |
| 【未取证】 | 没证据，**不猜** | — |
