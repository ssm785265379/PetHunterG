# Client Protocol Module Inventory

This is a static-consumer inventory from the locally exported AS3 sources at
`C:\Users\ssm\AppData\Local\Temp\pethunter-all-scripts\scripts`. The export
is not checked into Git. These notes identify what the client sends and reads;
they are not packet-capture evidence of the retired server's full contract.

## Common Envelope

- `CommandManager.as:279-340,343-430,433-484` maps ordinary feature IDs to
  `m=show&showId=<id>`, adds request parameters, and normally sends POST to
  `flash.do`.
- `APetHunter.as:133-162` splits a response on a tab, parses the first part as
  the command ID and the second as JSON, then dispatches the pair to the active
  UI's `readDatas`.
- `GameUtil.as:300-317` recognizes protocol errors shaped like `-1:<integer>`.
- A UI field read below is evidence that the client consumes the field, not
  proof that it is mandatory, nullable, or generated by a particular backend
  rule.

## Tasks, Home, Shop, Social

- **Task detail/reward:** `TASK_INFO=46` with `gid`; `TaskUI` reads `type,id,icon,condition`, reward fields (`reward_point`, `reward_money`, `reward_crystal`, `reward_goods`), `is_finish`, and `pic`. `TASK_REWARD=47` sends the current task data; its response checks `value="ok"` (`TaskItem.as:88`, `TaskUI.as:174-465`). `MainUI.as:84-89` routes 511 to the tracker and 46 to the task screen.
- **Home/menu:** `REQUEST_FUNCTION=502`; `GameUI.as:194-256,278-309` maps main buttons to local flows and function bits. Home requests `PLAYER_BASE_INFO=2`; fight, city, farm, friend, task, and help buttons use distinct local flows and gating checks.
- **Shop:** list `SHOP_LIST_INFO=27` with `p,n,ttype`; response consumes `list[]` and `shop_type`, with row fields including `team,id,type,money,point,crystal,need_goods_num,need_goods_id,icon` (`ShopListUI.as:132-223`). Details `SHOP_GOODS_INFO=28` sends `gid,ttype,loc`; UI reads `goods[]`, `shop_type`, `loc`, and `goods_ext` balances. Purchase `SHOP_BUY=29` sends `gid,ttype,loc`; visible result handling checks `value="ok"` (`ShopInfoUI.as:379-635`).
- **Friends:** list `FRIEND_LIST=51` with `p,n`, consumes `player_str_id` and `friend[]` rows (`id,state,name,img`) (`FriendUI.as:197-294`). Detail entry uses command 52 with `gid,psk=2`, then routes to player detail 3, which reads `show_type,player{id,name,lv,img},pets[]` (`FriendInfoUI.as:200-293`). Challenge/banquet use 53/54 with `gid`; their response contracts were not fully traced.
- **Guild:** command IDs 86-96 cover own guild, list/create/member/battle. `MY_GUILD=86` reads `guild_id,leader_img,guild_name,position,leader_name,mem_num`; guild list 88 reads `guilds[]` with `id,name,mem_num,max_mem_num,leader_name`; member list 91 reads `list[]` with `id,name,position,img`; battle info 94 reads `is_battle_on,battle_turn,isReward,start_time,end_time,total_honor,battle_team.turn{1,2,3}` (`SocietiesMyUI.as:155-247`, `SocietiesTopUI.as:150-199`, `SocietiesListUI.as:139-203`, `SocietiesWarUI.as:311-395`). Mutation response schemas remain partly unknown.

## Pets, Bag, Equipment

- **Pet list/detail:** `PET_LIST=11` sends `p,n`; reads `pet_num,max_pet_num,add_pet_card_num,own_card_num,pets[]`, where rows use `index,id,icon,name,lv,battle_state` (`PetListUI.as:46,157-175,201-260`). Detail `PET_BASE_INFO=12` sends `index`; reads `index,star,is_lockable,is_locked,icon,id,name,lv,pro`, and may read `free_goods_*` / `next_pet` data (`PetInfoUI.as:275-379,606-670`). **Implemented locally** in `server/pet_hunter_server/app.py` with a per-player `pets` table, paging by stable instance `index`, and tests in `server/tests/test_app.py`; verified on device 2026-10-21. Local capacity 30 (cap 90, +9) and the starter pack 火龙/小火猴 are documented local defaults, not recovered original-server values. Capacity lives in `players.pet_capacity`.
- **Pet mutations:** `PET_UP=14` (`index`) → client has no `case`, so the response must be the **new pet-detail object**. `PET_DEL=15` (`index`) → client reads optional `free_goods_id`; otherwise it goes back and the list re-requests 11. `PET_CHANGE_NAME=18` (`index,pName`) → client ignores the body and re-requests 12. `ADD_PET_COUNT=40` (no params) → client re-requests 11. `PET_LOCK=55` (`index`) → reads `value` and compares it to the **strings** `"true"`/`"false"` (`PetInfoUI.as:606-669`). **Implemented locally** with persistence and guards (locked pets cannot be evolved/released; `battle_state != 0` cannot be released; unknown/foreign `index` → `-1:506`); failures use the client's bundled `-1:<key>` codes so the game shows its own text rather than a network error. Catch is command 7 elsewhere; `HunterCatchUI` itself only shows result data and requests pet detail 12 (`HunterCatchUI.as:123-128`), so the actual catch caller still needs tracing.
- **Bag:** `BAG_INFO=22` sends `ttype,p,n`; response reads `bag_size,max_bag_size,goods_list[]`; rows use `team,id,index,icon,num,type,use_type`, and sometimes `level` (`BagListUI.as:154-228,257-370`). **Implemented locally** for all three tabs from a persisted `inventory` table; `bag_size` is reported per tab (local interpretation). Row `icon` must be the full class name `p<iconId>` because `IconItem` resolves it verbatim. Equipment rows must return `type: 0`: `BagListUI.onMouseUpItem` switches on that value and cases 1/2/9/24/25/27 are pet-item commands, so the equipment slot type must not land there; `default` + `ttype==3` sends `EQUIP_INFO`.
- **Equipment:** `EQUIP_INFO=39` sends `index,ttype=3`; response reads `money,index,id,icon,level,star,pro,hp,phy_att,mag_att,phy_def,mag_def,speed`, optionally `skills,buffs` (`EquipInfoUI.as:189-333`). The page has no `request()`: it is populated by the routed 39 response, so the click sends the command. `icon` here is numeric and the client prefixes `p`; `id` is looked up in `pic` with no try/catch, so only real equip ids/icons may be returned. `money>0` hides the sell button. **Implemented locally (read-only)** with a persisted equipment row; sale 68/69 and equip 37 are still unimplemented, so `money` is a positive local gate.
- **Blacksmith:** list 32 sends `ttype,loc,p,n`; detail 33 sends `ttype,gid`; make 34 (`gid`), refine 35 (`index`), enchant 36 (`index`). Detail parsers read item stats, skills/buffs, `need_*`, `own_*`, `need_goods`; refine additionally reads `next_refine`. Exact success-side state updates, especially enchant, need device validation (`BlacksmithListUI.as:159-253`, `MakeInfoUI.as:163-302`, `RefineInfoUI.as:137-356`, `EnchantInfoUI.as:169-316`).
- **Training:** overview 504; standby list 505 with `p,n`; detail 9 with `index`; training action 10 with `index,ttype`. The UI consumes list rows and training-result reward/experience fields, while client timers can trigger refreshes (`DevelopUI.as:98-135`, `DevelopPetListUI.as:146-181`, `DevelopPetInfoUI.as:143-194`, `DevelopResultUI.as:180-335`). Training formulas and authoritative resource changes are unknown.

## Unknowns That Must Stay Explicit

- Full server schemas, mandatory-vs-optional fields, types/enums, and server-side validation are not recoverable from UI property reads alone.
- No live packet capture has confirmed the statically observed response examples.
- Multi-step side effects (resource costs, save timing, retry/idempotency, battle rewards) need deterministic local tests and device checks.
- Error ID meanings and per-screen error handling are not exhaustively traced.
- The local AS3 export directory is temporary and not part of the Git repository; line references may need regeneration if the SWF export changes.
