# 本地服务端系统还原路线

日期：2026-10-21

## 目标与边界

在现有 Flask、SQLite 和 Android AIR 诊断客户端上逐项恢复个人本地游戏流程。保留现有账号、角色和原始游戏资产。以客户端 AS3 消费逻辑确定协议，以事务与持久化测试确定状态变化，以手机实际界面确定可用性。客户端字段不能证明原服数值公式；本地规则必须明确标注。

## 方案选择

推荐按依赖逐个完成可验证闭环。相比先把全部命令填成静态响应，这种方式能发现协议与存档问题；相比先做战斗，启动和宠物的协议依赖更小。

## 还原顺序

1. 账号与启动：登录已有账号、创建角色、读取 510、恢复会话、启动功能信息 502；确认退出重进仍能恢复角色。
2. 宠物：先还原 11 列表和 12 详情，核实分页、字段类型、图标和空列表；再按证据加入宠物持久化及改名、锁定等操作。
3. 背包与装备：22、39 查询，随后验证装备、使用、出售的事务与重试行为。
4. 商店：27、28 查询，再实现购买 29 与余额、物品同步变更。
5. 任务：511、46 查询，再实现条件推进与奖励 47 的防重复领取。
6. 狩猎与探索：4、5、98、99 查询；完整追踪战斗回放结构后实现战斗、捕捉与探索状态迁移。
7. 训练、家园、好友、公会：依赖前述持久化与资源系统逐项展开。支付及未追踪的协议保持未实现。

## 第一阶段设计

沿用现有 HTTP 入口及命令 ID 与 JSON 的制表符封装，不更换客户端协议。先通过手机登录现有账号，关联请求、响应与界面；检查当前重复注册返回通用错误的事实，不删除账号重试。若出现失败，先定位凭据校验、响应解析或 UI 回调的具体环节，再作最小修改。

角色创建成功必须落入现有 SQLite 数据库，每账号限一个角色。角色查询只能返回对应记录。自动登录必须校验账号密码与角色归属。502 的值必须从客户端调用点确定，不猜测标志位。

服务端修改先增加协议或状态回归测试，再实现；运行现有测试，保留原数据库进行真机验证。日志只保留命令、字段名、状态与长度，不记录密码、盐或哈希。

## 未实现命令的处置（已修正）

> **本节在 2026-10-22 被推翻并重写。** 早先的结论"未实现命令返回 501 以安全失败"是**错的**，
> 而且是设备上"网络错误"的唯一根因。

### 根因：501 是传输层失败，不是业务失败

`APetHunter.as:133-163` 只在**正常响应**时解析包体：`GameUtil.filter()` 去尾部 `\t` →
`split("\t")` → `shift()` 得 cmd 号 → `shift()` 得 JSON → `JSON.parse` → `readDatas`。

而 `APetHunter.as:166-168` 的 `ioHttpRequestError` 在**任何传输层失败**时弹出
`error.txt[0]`（"网络错误"）并 `flow(LOGIN)`。HTTP 501 恰好触发它。

结论：只要返回**正常状态码 + 合法信封**，客户端就会走自己的正常分支。
业务上"返回空数据"与"返回 501"对玩家的差别，是**一个可用页面**与**一个死掉的页面**。

### 已修正

兜底分支现在返回 `200` + `<showId>\t{"value":"ok"}`，并写 warning 日志。
这样 48 个未实现命令全部不再阻塞玩家。

### 为什么 501 从来不是"安全失败"

原文档称未实现命令返回 501 是"有意为之的安全失败"。实际后果是：

- 玩家在**副本（73）、竞技场结算（24）、公会（87/92/93/95）、探险（105）、排行榜（507）**
  等入口每点一次就弹一次"网络错误"，并被踢回登录页。
- 审计显示客户端共发送 **114** 个命令，服务端只实现了 **66** 个。
